**작성일:** 2026-03-09

## 1. 문서 개요

### 1-1. 이 문서의 역할

- **제품의 단일 정의 원천**: "AgentDesk란 무엇인가"에 대한 답을 이 문서에서 내린다.
- **다른 문서의 상위 문서**: [차별화 전략](strategy/claw-empire-differentiation-plan.md), [메뉴 스펙](design/agentdesk-2.0-menu-spec.md), [아키텍처](architecture/README.md), [API 스펙](specs/api.md) 등은 이 설계서의 관점을 따른다.
- **신규 합류자·외부 공유용**: 제품을 처음 접하는 사람이 한 번 읽고 전체 그림을 잡을 수 있게 한다.

### 1-2. 유지 원칙

- 제품 방향이 바뀔 때 **이 문서를 먼저 수정**한 뒤, 하위 전략·디자인·스펙을 정렬한다.
- 섹션별로 "상세는 ○○ 문서 참조"로 두고, 중복을 최소화한다.

## 2. 제품 비전 & 포지셔닝

### 2-1. 한 줄 정의

**AgentDesk는 "프로젝트 목표, 리스크, 의사결정, 산출물을 운영하는 프로젝트 운영체제(Project OS)"이다.**

- "AI 에이전트를 관리하는 툴"이 **아니라**
- "목표 달성 메커니즘을 운영하는 시스템"이다.

### 2-2. 포지셔닝 전환 (2.0)

| 구분 | 이전 | 2.0 |
|------|------|-----|
| 중심 개념 | CEO/CTO·직책 중심 조직 시뮬레이터 | **프로젝트·카테고리** 중심 Project OS |
| 첫인상 | 직책·조직 | 프로젝트 목표·리스크·게이트·산출물 |
| 확장성 | 특정 도메인(IT/투자) 예시에 묶임 | 사용자 정의 **카테고리**로 어떤 도메인에도 적용 |

### 2-3. 브랜드 메시지

- **KR:** "AgentDesk: 어떤 팀이든 맞춤 설계하는 프로젝트 운영체제"
- **EN:** "AgentDesk: A Project Operating System Tailored to Your Workflow"
- **서브카피:** "IT, 투자, 리서치, 운영. 템플릿으로 시작하고 당신의 방식으로 진화시키세요."

### 2-4. 소스 & 라이선스

- **AgentDesk 소스코드는 오픈소스이다.**  
- 공개 저장소에서 소스를 확인·포크·수정·재배포할 수 있으며, 라이선스 조건(저장소 또는 `LICENSE` 파일)을 따른다.
- 커뮤니티 기여·이슈·문서화는 제품 방향과 함께 이 설계서를 참고할 수 있다.

## 3. 목표 사용자 & 페르소나

### 3-1. 1차 대상

- **프로젝트를 실행·관리하는 주체**: 팀장, PM, 소규모 조직 리더.
- **목표:** 프로젝트의 목표·리스크·검증·산출물을 한 곳에서 보고, 에이전트(자동화)와 협업하고 싶은 사용자.

### 3-2. 사용 시나리오 (요약)

1. **프로젝트 시작:** 카테고리(또는 템플릿)를 선택하거나 직접 정의한 뒤, 프로젝트를 생성한다.
2. **일상 작업:** 대시보드에서 목표/리스크/게이트/산출물을 확인하고, 태스크 보드·팀(에이전트)·라이브러리에서 실행한다.
3. **검증·자산화:** 게이트 통과·산출물 품질을 추적하고, 필요 시 카테고리 정책을 조정한다.

### 3-3. 페르소나 (보완 시 참고)

- 구체적 페르소나(이름, 역할, 목표, 불편함)는 PRD 또는 전략 문서에서 확장할 수 있다.  
- 본 설계서에서는 "프로젝트 실행 주체·팀/소규모 조직" 수준으로 두고, 상세는 별도 문서에서 다룬다.

## 4. 핵심 원칙

제품 설계·기능 추가 시 지키는 원칙이다.

| 원칙 | 설명 |
|------|------|
| **프로젝트 우선** | 진입점은 "어떤 프로젝트인가"이다. 직책(CEO/CTO)이 아닌 프로젝트·카테고리가 최상위 컨텍스트다. |
| **카테고리는 사용자가 설계한다** | IT/투자 등은 "예시 템플릿"일 뿐이다. 사용자가 카테고리를 만들고 KPI·게이트·산출물 규칙을 붙일 수 있어야 한다. |
| **실행 단위는 유지** | 부서·에이전트(팀)는 기존처럼 "실행 단위·역할"이다. 카테고리는 그 위에 "이 프로젝트를 어떤 규칙으로 운영할지"를 정의하는 레이어다. |
| **재현성** | 프로젝트 생성 시점의 카테고리 버전을 고정한다. 이후 카테고리 수정은 기존 프로젝트에 자동 반영되지 않는다. |
| **로그인 없이 시작** | 진입은 앱 실행 → (선택) 프로젝트/카테고리 컨텍스트 → 대시보드/작업. 인증 정책은 별도 요구사항에서 다룬다. |

## 5. 제품 구조 (High-Level)

### 5-1. 공통 코어 (모든 프로젝트 공통)

- **목표 계층:** Objective → Initiative → Task → Deliverable  
- **운영 정책:** 우선순위, 승인, 예산, 리스크 정책  
- **실행 엔진:** 에이전트 배정, 자동 재정렬, 병목 감지  
- **검증 엔진:** 품질 게이트, 완료 조건, 감사 로그  
- **자산화:** 결과물 품질 점수, 재사용 추천  

### 5-2. 카테고리 시스템 (2.0 핵심)

- **카테고리** = 프로젝트 "유형"의 정의. 목표/정책/게이트/산출물 스키마를 가진다.
- **기본 템플릿:** IT Delivery, Software Development, Investment Ops, Research/Strategy, Marketing/Growth, Custom Blank. (상세: [차별화 전략 §3-2](strategy/claw-empire-differentiation-plan.md))
- **사용자 정의 카테고리:** 이름·아이콘·색상, KPI·리스크·게이트·산출물 스키마, 라우팅 정책을 사용자가 정의·복제·버전 관리할 수 있다.

### 5-3. 정보 구조 관계 (개념)

```
[Category] ──버전 고정──► [Project] ──소속──► [Department / Agent]
     │                         │
     │ kpi_schema,              │ success_metric,
     │ risk_schema,             │ risk_profile,
     │ gate_schema,             │ required_gates,
     │ deliverable_schema       │ deliverable_schema (상속·오버라이드)
```

- 상세 데이터 모델(필드·테이블)은 [차별화 전략 §4](strategy/claw-empire-differentiation-plan.md) 및 API/DB 스펙을 따른다.

제품이 제공하는 기능을 영역별로 나눈 것이다. 우선순위·Phase는 로드맵 문서를 따른다.

| 영역 | 설명 | 참조 |
|------|------|------|
| **프로젝트·카테고리** | 프로젝트 생성/선택, 카테고리 선택·정의·편집, 버전 고정·정책 주입 | 차별화 전략 §3-2, §4 |
| **대시보드** | 목표/리스크/게이트/산출물 4분면, 카테고리별 위젯 | 메뉴 스펙, 차별화 전략 §5, [UX 스펙 §6](design/ux-renewal-2.0.md) |
| **태스크** | 태스크 보드, 산출물(Deliverables), 스케줄러 | 기존 기능 유지, 팩·카테고리와 연동 |
| **팀(에이전트)** | 에이전트·부서 관리, Heartbeat, 프로젝트 팀 구성 | 기존 기능 유지, "Agents" → "Team" 용어 전환, [UX 스펙 §11-A·B](design/ux-renewal-2.0.md) |
| **라이브러리** | Skills, Agent Rules, Memory, Hooks | 기존 기능 유지 |
| **오피스** | 픽셀 오피스 캔버스, 부서·에이전트 시각화 | 기존 기능 유지 |
| **설정** | 회사/앱 설정, **카테고리 에디터** 진입(탭 또는 서브메뉴) | 메뉴 스펙, 차별화 전략 §5 |
| **CLI·Lounge** | CLI 사용량, 라운지(게임룸) | 기존 기능 유지 |

## 7. 사용자 경험 원칙 (UX)

### 7-1. 진입·최상위

- **첫 화면:** 로고 + **현재 프로젝트**(이름·카테고리 배지). CEO/회사명 노출 제거.
- **프로젝트 없을 때:** 상단 클릭 → "새 프로젝트" 또는 "카테고리 선택 후 생성". (Phase 2 상세 플로우는 메뉴 스펙·전략 문서 참조.)

### 7-2. 네비게이션

- **1번 메뉴:** 대시보드(프로젝트 성과 한눈에 = "홈").
- **순서:** Dashboard → Office → Tasks → Team → Library → CLI Usage → Lounge → Settings.  
- 상세 메뉴 구조·라벨은 [메뉴 스펙](design/agentdesk-2.0-menu-spec.md)을 따른다.

### 7-3. 온보딩·프로젝트 생성

- **온보딩:** "직책 선택"이 아닌 "프로젝트 카테고리 선택/생성". 템플릿 또는 Custom Blank.
- **프로젝트 생성:** 카테고리 선택 시 KPI/게이트/산출물 기본값 자동 주입, 필요 시 미리보기 제공.

### 7-4. 카테고리 에디터

- 노코드 수준(폼·드롭다운·체크박스). 고급 사용자용 JSON 편집은 선택.
- 저장 시 버전 증가, 기존 프로젝트 영향도 안내.

## 8. 용어 정의

| 용어 | 정의 |
|------|------|
| **Project OS** | 프로젝트 실행 자체를 운영하는 운영체제라는 제품 포지셔닝. |
| **Category** | 프로젝트 유형의 정의. KPI·리스크·게이트·산출물 스키마와 라우팅 정책을 가짐. |
| **Category version** | 카테고리 스키마의 버전. 프로젝트 생성 시 고정되어 재현성을 보장. |
| **Project** | 사용자가 실행하는 단위. 하나의 카테고리(및 버전)에 연결되고, success_metric·risk_profile·required_gates·deliverable_schema 등을 가짐. |
| **Gate** | 검증 단계. 완료 조건·품질 기준 등. |
| **Deliverable** | 필수 산출물. 카테고리/프로젝트별 스키마로 정의. |
| **Department / Agent** | 실행 단위·역할. 카테고리가 정한 정책 안에서 태스크를 수행하는 주체. (기존 "부서·에이전트" 유지.) |
| **Team** | 메뉴에서 "Agents"를 대체하는 2.0 용어. 같은 기능, Project OS 톤. |

## 9. 비기능 요구사항 (요약)

- **진입:** 로그인 없이 앱 실행 가능(정책에 따라 인증 레이어 추가 가능).
- **데이터:** 프로젝트·카테고리 데이터는 기존 DB와 마이그레이션 정책에 따라 호환 유지.
- **성능·보안:** 일반 웹 앱 수준. 상세는 아키텍처·보안 요구사항 문서에서 다룬다.
