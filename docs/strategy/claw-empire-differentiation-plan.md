# AgentDesk 차별화 전략 (Project OS 버전)

작성일: 2026-03-09
목표: "Claw-Empire 기반" 인상을 넘어서, 사용자 누구나 원하는 종류의 프로젝트를 설계/운영하는 **프로젝트 운영체제(Project Operating System)** 로 포지셔닝

## 1. 포지셔닝 전환

기존: CEO/CTO 중심 조직 시뮬레이터
전환: **프로젝트 실행 자체를 운영하는 OS**

핵심 메시지:
- "AgentDesk는 AI 에이전트를 관리하는 툴"이 아니라
- "프로젝트 목표, 리스크, 의사결정, 산출물을 운영하는 시스템"

중요 원칙:
- IT/투자는 **예시 카테고리**일 뿐
- 실제로는 사용자가 카테고리를 직접 만들고 운영 규칙을 붙일 수 있어야 함

## 2. 왜 Project OS가 맞는가

1. 시장 확장성
- IT, 투자, 리서치, 마케팅, 교육, 운영, 법무 등 어떤 프로젝트에도 적용 가능

2. 차별화 강도
- 일반 오케스트레이션 툴은 "에이전트 실행" 중심
- Project OS는 "목표 달성 메커니즘" 중심

3. 사용자 체감 변화
- 직책(CEO/CTO)이 아니라
- 프로젝트 성과(목표/리스크/검증/산출물) 중심으로 경험이 설계됨

## 3. 제품 구조: 공통 코어 + 카테고리 시스템

## 3-1. 공통 코어 (모든 프로젝트 공통)

- 목표 계층: Objective -> Initiative -> Task -> Deliverable
- 운영 정책: 우선순위/승인/예산/리스크 정책
- 실행 엔진: 에이전트 배정, 자동 재정렬, 병목 감지
- 검증 엔진: 품질 게이트, 완료 조건, 감사 로그
- 자산화: 결과물 품질 점수, 재사용 추천

## 3-2. 카테고리 시스템 (핵심)

### A) 기본 카테고리 템플릿 제공

- IT Delivery
- Software Development (소프트웨어 개발)
- Investment Ops
- Research/Strategy
- Marketing/Growth
- Custom Blank: KPI/게이트/산출물을 처음부터 정의하는 빈 카테고리(템플릿 없음)

역할:
- 신규 사용자가 빠르게 시작할 수 있는 출발점
- "정답"이 아니라 "샘플"로 제공

### B) 사용자 정의 카테고리 생성

사용자가 직접 정의 가능:
- 카테고리 이름/아이콘/색상
- KPI 세트
- 리스크 모델
- 필수 게이트
- 필수 산출물 스키마
- 자동 라우팅 규칙

즉, "투자"나 "IT"가 아니라 "내 팀 방식"을 제품 안에 모델링 가능해야 함.

### C) 카테고리 상속/복제

- 기존 카테고리를 복제해서 변형
- 팀/조직별 버전 관리
- 프로젝트 시작 시 카테고리 버전 고정(재현성)

## 4. 데이터 모델 변경 제안

### 4-1. 기존 모델과의 관계

- **카테고리** = 프로젝트 유형(목표/정책/게이트 정의). 프로젝트 생성 시 "어떤 방식으로 운영할지"를 결정.
- **부서/팀/직책**(기존) = 실행 단위·역할. 카테고리가 정한 정책 안에서 작업을 수행하는 주체.
- 즉 카테고리는 **추가 레이어**이며, 기존 조직 구조를 대체하지 않고 "이 프로젝트는 어떤 카테고리 규칙을 따르는가"를 붙이는 형태.

### 4-2. 프로젝트 엔티티

- `category_id`: 사용자 정의 카테고리 참조
- `category_version`: 프로젝트 생성 시점 카테고리 버전(재현성 보장)
- `success_metric`: 프로젝트 성공 기준(JSON). 카테고리 `kpi_schema`를 **구체화·오버라이드**한 값(프로젝트별 목표 수치 등).
- `risk_profile`: 리스크 기준/임계치(JSON). 카테고리 `risk_schema` 기본값 + 프로젝트별 조정 가능.
- `required_gates`: 필수 게이트 배열
- `deliverable_schema`: 필수 산출물 타입 정의(카테고리 스키마 상속 후 프로젝트별 추가 가능)

### 4-3. 카테고리 엔티티

- `name`, `slug`, `description`
- `kpi_schema`, `risk_schema`, `gate_schema`, `deliverable_schema`
- `routing_policy`
- `is_template`, `version`
- `owner_scope`: 소유 범위. 예: `global`(시스템 템플릿), `org`, `team`. 스코프별 권한: global=읽기만, org/team=쓰기·복제·버전 관리.

## 5. UX 변경 제안 (직책 중심 -> 카테고리 중심)

1. 온보딩
- "직책 선택" 대신 "프로젝트 카테고리 선택/생성"
- 템플릿에서 시작 or 빈 카테고리(Custom Blank)에서 시작
- **직책(CEO/CTO/팀장) 선택 UI**: Phase 1 완료 시점부터 신규 플로우에서는 숨기고, 기존 사용자용 레거시 경로만 유지. 완전 제거는 Phase 2 안정화 후 검토.

2. 프로젝트 생성
- 카테고리 선택 시 KPI/게이트/산출물 기본값 자동 주입
- 생성 전 "이 카테고리로 무엇이 자동화되는지" 미리보기 제공

3. 대시보드
- 공통 4분면: 목표 / 리스크 / 게이트 / 산출물
- 카테고리에 따라 위젯 세부 항목만 바뀜

4. 카테고리 에디터
- 노코드 수준의 정책 편집 UI(폼 기반 필드 + 드롭다운/체크박스). 고급 사용자용 JSON 직접 편집은 선택 옵션.
- 스키마 검증 및 저장 전 에러 메시지로 필수 필드/형식 안내.
- 저장 시 버전 증가, 기존 프로젝트 영향도 표시

## 6. 실무 문구(브랜딩) 제안

- KR: "AgentDesk: 어떤 팀이든 맞춤 설계하는 프로젝트 운영체제"
- EN: "AgentDesk: A Project Operating System Tailored to Your Workflow" (또는 "You Can Model to Your Workflow" — 맞춤 설계 vs 모델링 뉘앙스에 따라 선택)

서브카피 예시:
- "IT, 투자, 리서치, 운영. 템플릿으로 시작하고 당신의 방식으로 진화시키세요."

## 7. 60일 실행 로드맵

### Phase 1 (0-20일): 카테고리 기반 전환

- 용어 전환: CEO/CTO 카피 축소, Project OS + Category OS 카피 적용
- `category`/`category_version` 데이터 모델 추가
- 기본 템플릿 3~5개 제공

### Phase 2 (21-40일): 사용자 정의 카테고리 MVP

- 카테고리 CRUD
- KPI/리스크/게이트/산출물 스키마 편집
- 프로젝트 생성 시 카테고리 **자동 주입**: 선택한 카테고리의 `category_version` 고정 + 해당 버전의 KPI/게이트/산출물 기본값을 프로젝트 필드에 복사. 이후 카테고리 수정은 기존 프로젝트에 반영되지 않음.

### Phase 3 (41-60일): 자동화/자산화

- KPI 기반 우선순위 재정렬
- 리스크 임계치 자동 홀드 + 액션 제안
- 산출물 재사용 추천 + 카테고리별 성과 비교

## 8. 바로 생성할 개발 티켓

**Phase 1–2 (모델·CRUD·UI):**
- `feat(category): category/category_version 스키마 추가`
- `feat(category): 기본 템플릿 시드(IT/Software Development/Investment/Research/Marketing/Custom)`
- `feat(category): 카테고리 CRUD + 버저닝 API`
- `feat(ui): 카테고리 선택형 프로젝트 생성 플로우`
- `feat(ui): 카테고리 에디터(정책/KPI/게이트/산출물)`
- `feat(project): 프로젝트 생성 시 카테고리 버전 고정 및 정책 기본값 주입`

**Phase 3 (엔진 연동):**
- `feat(engine): 카테고리 정책 기반 자동 라우팅/홀드`

## 9. 결론

맞는 방향입니다.
핵심은 "특정 카테고리 지원"이 아니라 **카테고리를 유저가 설계하게 만드는 것**입니다.
AgentDesk가 이 구조를 가지면, IT/투자 예시는 시작점이 되고 제품은 훨씬 넓은 시장으로 확장됩니다.
