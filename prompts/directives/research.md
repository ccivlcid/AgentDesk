## 기술스택
- 언어/도구: (예: Python, Jupyter, Node.js, R 등)
- 주요 라이브러리: (예: requests, BeautifulSoup, LangChain, Scrapy 등)
- 문서화: (예: Markdown, Notion, Obsidian, Google Docs 등)
- 데이터 저장: (예: JSON, SQLite, Google Sheets, Airtable 등)

## 목표
특정 주제에 대해 **체계적으로 조사하고, 발견한 것을 명확히 기록**하는 것이 목표다.
이 프로젝트의 산출물은 코드가 아니라 **발견과 인사이트가 담긴 문서**다.

## 작업 원칙
- **결론보다 과정을 기록**한다. "무엇을 시도했고, 뭘 알게 됐고, 뭘 모르는지"가 핵심 산출물이다.
- 실패한 접근법도 반드시 문서화한다. 왜 실패했는지를 기록하면, 같은 실수를 반복하지 않을 수 있다.
- 코드 품질보다 발견(finding)의 질이 중요하다. 스크립트가 지저분해도 정확한 결과를 내면 된다.
- 빠르게 시도하고, 배운 것을 즉시 기록한다. 기억에 의존하지 않는다.
- **가설을 먼저 세우고 실험**한다. "일단 해보자"가 아니라 "X이면 Y일 것이다"를 명시한 후 검증한다.
- 스코프 크립(scope creep)을 경계한다. 하나의 질문에 답하는 데 집중하고, 새로운 질문은 기록만 해둔다.
- 데이터 출처(source)를 반드시 기록한다. URL, 문서명, 접근 일시, API 버전 등.
- 정량적 결과에는 측정 방법과 한계를 명시한다. "정확도 95%"만 적지 말고, 어떤 데이터셋에서 어떤 방법으로 측정했는지 적는다.
- 주관적 판단과 객관적 사실을 구분하여 기록한다. "이것은 빠르다"(주관) vs "응답 시간이 120ms다"(객관).

## 태스크 분해
- **선형 진행이 아닌 반복 루프**:
  1. **스코프 정의**: 조사 범위와 핵심 질문 목록 작성. "이 조사가 끝나면 뭘 알게 되는가?"
  2. **개별 조사/실험** (병렬 가능): 각 질문에 대한 독립적인 조사. 웹 리서치, 코드 실험, 벤치마크 등.
  3. **중간 정리**: 지금까지 발견한 것 요약 + 남은 질문 업데이트 + 방향 재조정.
  4. **종합 보고**: 발견 사항 종합 + 결론 + 한계 인식 + 다음 단계 제안.
- 각 조사/실험은 독립적으로 실행 가능해야 한다. 선행 조사 결과에 의존하는 경우 명시한다.
- 예상치 못한 발견이 있으면 새 질문으로 분기해도 된다. 단, 원래 스코프를 잊지 않는다.
- 코드가 필요한 경우, 재사용성보다 일회성 스크립트로 빠르게 작성한다.

## 품질 기준
- **"이 조사로 뭘 알게 됐는가?"에 답할 수 없으면 다음 단계로 넘어가지 않는다.**
- 결과 문서 필수 항목:
  - 질문: 무엇을 알고 싶었는가?
  - 방법: 어떻게 조사/실험했는가?
  - 결과: 무엇을 발견했는가? (데이터, 스크린샷, 로그 포함)
  - 결론: 이것이 무엇을 의미하는가?
  - 한계: 이 결과를 신뢰할 수 없는 이유는 무엇인가?
  - 다음 질문: 이 결과로 인해 새로 생긴 질문은?
- 코드 품질은 "다른 사람이 읽고 같은 결과를 재현할 수 있는 수준"이면 충분하다.
- 자동화 테스트는 필수가 아니다. 단, 결과의 정확성은 수동으로라도 반드시 확인한다.

## 리뷰
- 코드 리뷰 대신 **결과 리뷰**를 한다. 리뷰 관점:
  - 이 발견이 원래 질문에 답하고 있는가?
  - 결론이 데이터에 의해 뒷받침되는가? 논리적 비약은 없는가?
  - 편향(confirmation bias)은 없는가? 결론이 먼저 정해진 조사가 아닌가?
  - 다음 질문/가설이 합리적인가?
- **planning 에이전트**가 방향성을 판단한다: 더 파야 하는가, 여기서 멈출 것인가, 방향을 전환할 것인가.
- 코드의 정리/리팩토링은 리뷰하지 않는다. 결과의 정확성과 문서의 완전성만 본다.

## 우선순위
```
인사이트 질 > 문서 완전성 > 속도 > 코드 품질
```
- 빠르게 검증하되, 배운 것은 반드시 기록한다.
- "완벽한 답"보다 "충분히 좋은 답 + 명확한 한계 인식"이 더 가치 있다.
- 한 주제를 끝없이 파기보다, 적절한 시점에 결론을 내리고 다음으로 넘어간다.
