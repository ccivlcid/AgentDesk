## 기술스택
- 프론트엔드: (예: React, Vue, Svelte 등)
- 백엔드: (예: Node.js/Express, Django, Spring 등)
- DB: (예: PostgreSQL, MySQL, MongoDB 등)
- 인프라: (예: Docker, AWS, Vercel 등)
- 패키지 매니저: (예: pnpm, npm, yarn 등)

## 목표
프론트엔드 + 백엔드 + DB + 인증을 포함하는 **프로덕션 수준의 풀스택 애플리케이션**을 구축한다.
실제 사용자에게 배포할 수 있는 완성도를 목표로 하며, 유지보수와 확장을 염두에 둔 아키텍처를 설계한다.

## 작업 원칙
- 프로덕션 수준의 코드를 작성한다 — 에러 핸들링, 로깅, 입력 검증은 필수다.
- 아키텍처 결정에는 ADR(Architecture Decision Record) 또는 코드 주석으로 "왜 이 선택을 했는지" 이유를 남긴다.
- DRY 원칙을 따르되, **3번 이상 반복**될 때만 추상화한다. 2번은 복사해도 된다.
- API 계약(스키마)을 프론트/백 합의 후 각자 병렬 구현한다. 계약 없이 프론트 구현 시작 금지.
- DB 스키마 변경은 반드시 마이그레이션 파일로 관리한다. 수동 ALTER TABLE 금지.
- 환경별(dev/staging/prod) 설정을 분리한다. 환경 변수 기반 설정 필수.
- 시크릿(API 키, DB 비밀번호 등)은 코드에 절대 하드코딩하지 않는다. 환경 변수 또는 시크릿 매니저 사용.
- 외부 API 호출에는 타임아웃과 재시도(retry) 로직을 포함한다.
- 모든 사용자 입력은 서버 측에서 검증한다. 클라이언트 검증만으로는 불충분하다.

## 태스크 분해
- **레이어별 분리**가 기본이다:
  1. DB 스키마 설계 + 마이그레이션
  2. API 엔드포인트 (인증/인가 포함)
  3. 비즈니스 로직 (서비스 레이어)
  4. UI 컴포넌트 + 페이지
  5. 통합 테스트 + E2E 테스트
- API 계약(OpenAPI spec 또는 타입 정의)을 먼저 확정한 후 프론트엔드 착수. 계약 미확정 상태에서 UI 구현 금지.
- 병렬 가능한 작업(예: 독립된 API 엔드포인트들, 서로 무관한 UI 페이지들)은 동시 진행한다.
- 인증/인가 레이어를 초반에 구축한다. 모든 후속 기능이 이에 의존하므로 블로커가 되지 않게 빠르게 완성.
- DB 마이그레이션은 코드 변경과 별도 태스크로 분리한다.

## 품질 기준
- 비즈니스 로직에 단위 테스트 필수. 커버리지 목표 70% 이상.
- API에 입력 검증(zod, joi, class-validator 등)과 일관된 에러 응답 포맷 필수.
- DB 마이그레이션은 롤백 가능하게 작성한다 (up + down).
- 프론트엔드: 주요 유저 플로우에 대한 통합 테스트 또는 E2E 테스트 1개 이상.
- API 응답에 적절한 HTTP 상태 코드를 사용한다 (200, 201, 400, 401, 403, 404, 500).
- N+1 쿼리를 금지한다. ORM 사용 시 쿼리 로그를 확인한다.
- 민감 데이터(비밀번호, 토큰)는 로그에 절대 출력하지 않는다.

## 리뷰
- 3라운드 리뷰:
  - **dev**: 기능 정확성, 코드 품질, 아키텍처 일관성
  - **qa**: 안정성, 엣지케이스, 에러 시나리오
  - **devsecops**: 보안, 인증/인가 누락, 인프라 설정
- 각 라운드에서 자기 관점에만 집중한다. dev가 보안을, devsecops가 UX를 리뷰할 필요 없다.
- DB 스키마 변경, 인증 로직 변경, API 계약 변경은 전원 리뷰.
- 머지 전 전체 테스트 스위트 통과 필수.

```
품질 ≈ 확장성 > 보안 > 속도
```
