## 기술스택
- IaC: (예: Terraform, Pulumi, CDK, Ansible 등)
- CI/CD: (예: GitHub Actions, GitLab CI, Jenkins, ArgoCD 등)
- 컨테이너: (예: Docker, Podman, Kubernetes, Helm 등)
- 클라우드: (예: AWS, GCP, Azure 등)
- 모니터링: (예: Prometheus, Grafana, Datadog 등)
- 스크립트: (예: Bash, Python, Makefile 등)

## 목표
인프라와 배포 파이프라인을 **코드로 관리**하고, 실패에 강하며 자동 복구 가능한 시스템을 구축한다.
새벽 3시에 실패해도 자동으로 알림이 가고, 가능하면 자동 복구되며, 최악의 경우 5분 안에 수동 롤백이 가능해야 한다.

## 작업 원칙
- **멱등성(Idempotency)은 필수**다. 같은 스크립트를 10번 돌려도 결과가 같아야 한다. "두 번 실행하면 깨지는 스크립트"는 버그다.
- 모든 변경은 코드(IaC)를 통해서만 적용한다. 콘솔에서 클릭으로 만든 리소스는 반드시 코드로 재정의한다. 수동으로 서버에 SSH 접속해서 설정을 바꾸는 것은 금지.
- **dry-run 모드를 기본 제공**한다. 프로덕션에 적용하기 전에 항상 dry-run으로 변경 사항을 미리 확인한다.
- 실패 시 자동 롤백이 가능하거나, 수동 롤백 절차가 문서화되어 있어야 한다. 롤백 절차가 없는 배포는 금지.
- 모든 파이프라인 단계에 로깅과 알림(Slack, PagerDuty, 이메일)을 포함한다. 실패했는데 아무도 모르는 상황이 가장 위험하다.
- 시크릿은 환경 변수 또는 시크릿 매니저(Vault, AWS Secrets Manager, GCP Secret Manager)로만 관리한다. git에 시크릿이 커밋되면 즉시 로테이션.
- 모든 변경은 PR을 통해서만 적용한다. main 브랜치 직접 푸시 금지.
- 비용을 의식한다. 새 리소스를 프로비저닝할 때 월 예상 비용을 계산하고 명시한다.

## 태스크 분해
- 각 스크립트/파이프라인 스텝이 **독립적으로 실행·실패·재시도** 가능하게 구성한다. 한 스텝이 실패해도 다른 스텝에 영향을 주지 않아야 한다.
- 인프라 변경과 애플리케이션 변경을 분리한다. 동시 배포 금지.
- 순서:
  1. **인프라 프로비저닝**: VPC, 서브넷, 보안 그룹, 로드밸런서, DB 인스턴스
  2. **네트워킹/보안**: 방화벽 규칙, SSL 인증서, IAM 역할/정책
  3. **CI/CD 파이프라인**: 빌드, 테스트, 배포 자동화. 브랜치별 전략(main=prod, develop=staging).
  4. **모니터링/알림**: 메트릭 수집, 대시보드, 알림 규칙(CPU > 80%, 에러율 > 1%, 디스크 > 90%).
  5. **문서화**: 아키텍처 다이어그램, 장애 대응 런북(runbook), 온콜 가이드.
- 배포 전략(카나리, 블루-그린, 롤링)을 초기에 결정한다.
- 재해 복구(DR) 시나리오를 별도 태스크로 작성하고 실제로 테스트한다.

## 품질 기준
- dry-run 테스트 통과 필수. dry-run 없이 프로덕션 적용 금지.
- 프로덕션 적용 전 스테이징 환경에서 동일한 변경을 먼저 적용하고 검증한다.
- 실패 시 알림이 정상 동작하는지 확인한다. 알림 테스트(fake failure)를 주기적으로 수행한다.
- 롤백 절차가 문서화되어 있고, 실제로 롤백 테스트를 수행한다. "롤백 가능하다고 생각한다"는 불충분.
- 인프라 드리프트(drift) 감지를 설정한다. 코드와 실제 상태가 다르면 알림.
- 파이프라인 실행 시간 목표: 빌드+테스트+배포 전체 15분 이내.
- 시크릿이 로그, 환경 변수 출력, git history에 노출되지 않는지 확인한다.

## 리뷰
- **핵심 질문: "이게 새벽 3시에 실패하면 어떻게 되는가?"**
- 리뷰 관점:
  - 에러 핸들링: 실패 시 파이프라인이 어떻게 동작하는가? 알림이 가는가?
  - 롤백: 이 변경을 되돌릴 수 있는가? 얼마나 걸리는가?
  - 시크릿: 시크릿이 노출될 수 있는 경로가 있는가?
  - 비용: 예상치 못한 과금이 발생할 수 있는가?
- 인프라 변경(IAM, 네트워크, 스토리지)은 특히 신중하게 리뷰한다. 실수하면 서비스 전체가 내려간다.
- "동작한다"만으로는 부족하다. "실패했을 때 어떻게 되는가"를 검증해야 한다.

## 우선순위
```
신뢰성 ≫ 보안 > 가시성(모니터링) > 비용 효율 > 편의성
```
- "자동화가 실패 없이 돌아가는 것"이 최고 목표.
- 편의성을 위해 신뢰성을 타협하지 않는다.
