## 기술스택
- 언어: (예: TypeScript, Python, Rust, Go 등)
- 빌드/번들러: (예: tsup, rollup, setuptools, cargo 등)
- 테스트: (예: Vitest, pytest, cargo test 등)
- 패키지 레지스트리: (예: npm, PyPI, crates.io 등)
- 문서: (예: TypeDoc, Sphinx, mdBook, Docusaurus 등)

## 목표
외부 개발자가 **5분 안에 설치하고 사용**할 수 있는 오픈소스 라이브러리/SDK를 만든다.
API 설계의 우아함, 문서의 완전성, 하위 호환성이 핵심이다.
한번 공개한 API는 제거하기 매우 어렵다는 사실을 항상 의식한다.

## 작업 원칙
- **공개 API 표면적을 최소화**한다. 내부 구현을 노출하지 않는다. `export`하는 것은 곧 계약이다.
- 모든 public 함수/클래스에 JSDoc/docstring을 작성한다. 파라미터, 반환값, 예외, 사용 예제를 포함한다.
- README, CHANGELOG, CONTRIBUTING, LICENSE를 필수로 포함한다. 이 중 하나라도 없으면 미완성이다.
- **시맨틱 버저닝(SemVer)**을 엄격히 따른다. patch=버그 수정, minor=기능 추가(하위호환), major=breaking change.
- 하위 호환성을 깨는 변경은 메이저 버전업 + 마이그레이션 가이드 + CHANGELOG 항목 필수.
- 의존성(dependencies)을 최소화한다. 외부 dep 추가 시 "이 라이브러리 없이는 정말 안 되는가?" 질문에 답해야 한다.
- 에러 메시지는 친절하게 작성한다. "뭐가 잘못됐고, 어떻게 고치는지"를 포함한다. 스택트레이스만 던지지 않는다.
- TypeScript라면 `.d.ts` 타입 정의의 정확성이 코드만큼 중요하다. IDE 자동완성이 정확히 동작해야 한다.
- 내부 코드와 공개 API를 명확히 분리한다. `internal/`, `_private` 접두사, 또는 package.json exports 필드를 활용한다.

## 태스크 분해
- 순서:
  1. **API 설계**: 공개 인터페이스(타입, 함수 시그니처, 클래스 구조)를 먼저 확정한다. 구현 전에 API를 확정.
  2. **핵심 구현**: 내부 로직 구현. API 시그니처는 이 단계에서 바꾸지 않는다.
  3. **테스트**: 커버리지 90%+. 정상 케이스, 엣지케이스, 에러 케이스 모두 포함.
  4. **문서화**: API 레퍼런스 + 사용 가이드 + 예제 코드(examples/).
  5. **CI/CD + 배포 설정**: 테스트 자동화, 린트, 버전 관리, 패키지 퍼블리시.
- **문서 없는 기능은 완료로 간주하지 않는다.** 코드가 아무리 완벽해도 문서가 없으면 미완성.
- 예제 코드(`examples/`)는 별도 태스크로 작성한다. 예제가 실제로 실행 가능해야 한다(CI에서 검증).
- CONTRIBUTING.md(기여 가이드)를 초기에 작성한다. 개발 환경 설정, 테스트 실행, PR 규칙을 포함.

## 품질 기준
- 테스트 커버리지 **90% 이상**. 엣지케이스(빈 입력, null, 극단값)와 에러 케이스(잘못된 타입, 네트워크 실패) 포함.
- 모든 exported 심볼에 타입 정의 정확. TypeScript `d.ts` 또는 Python `py.typed`.
- 예제 코드가 CI에서 실제로 빌드·실행 가능해야 한다. 깨진 예제는 문서가 없는 것보다 나쁘다.
- 브레이킹 체인지 시 마이그레이션 가이드 + CHANGELOG 항목 필수.
- 번들 사이즈 트래킹: size-limit 또는 유사 도구 적용. PR마다 사이즈 변화를 확인.
- tree-shaking 지원 (ESM export). 사용하지 않는 코드가 최종 번들에 포함되지 않아야 한다.
- zero-dependency가 이상적. 의존성이 있다면 `peerDependencies`로 분류할 수 있는지 검토.

## 리뷰
- **핵심 질문: "이걸 처음 보는 외부 개발자가 5분 안에 설치하고 사용할 수 있는가?"**
- 리뷰 관점:
  - DX(개발자 경험): 에러 메시지가 친절한가? 타입 추론이 정확한가? IDE 자동완성이 잘 동작하는가?
  - API 일관성: 비슷한 기능의 함수가 비슷한 패턴을 따르는가?
  - 문서 완전성: 모든 public API에 설명과 예제가 있는가?
- public API 변경 시 반드시 전원 리뷰.
- 브레이킹 체인지는 별도 승인. RFC(Request for Comments) 프로세스 권장.

## 우선순위
```
DX(개발자 경험) > API 설계 > 문서 > 테스트 > 성능 > 기능 수
```
- "많은 기능"보다 "적지만 완벽한 API". 나중에 추가는 쉽지만 제거는 거의 불가능하다.
- v1.0 전에는 자유롭게 API를 변경할 수 있지만, v1.0 이후에는 SemVer를 엄격히 지킨다.
