## 기술스택
- 언어: (예: TypeScript, Python, Go 등)
- 프레임워크: (예: Next.js, FastAPI, Express 등)
- DB: (예: PostgreSQL, SQLite, MongoDB 등)
- 기타: (예: Docker, Redis, S3 등)

## 목표
이 프로젝트의 유일한 목표는 **핵심 가설을 가장 빠르게 검증하는 것**이다.
완성도 있는 제품이 아니라, "이 아이디어가 동작하는가?"를 확인할 수 있는 최소한의 동작 가능한 프로토타입(Walking Skeleton)을 만든다.

## 작업 원칙
- **동작하는 최소 버전**을 최우선으로 만든다. 완벽하지 않아도 된다.
- 엣지케이스는 전부 무시한다. 하드코딩, 매직 넘버, 하드코딩된 설정값 모두 허용.
- 외부 라이브러리, SaaS, 보일러플레이트, 코드 생성기를 적극 활용해서 직접 코딩하는 양을 최소화한다.
- `TODO`, `HACK`, `FIXME` 주석을 남기고 빠르게 넘어간다. 지금 완벽하게 만들 필요 없다.
- 리팩토링, 추상화, 디자인 패턴 적용은 검증 이후로 미룬다.
- "유저가 직접 써보고 피드백을 줄 수 있는 상태"가 완료 기준이다.
- 인프라 자동화(CI/CD, IaC)는 하지 않는다. 수동 배포로 충분하다.
- 에러 핸들링은 `console.error` + 사용자에게 보여줄 최소한의 메시지면 충분하다.
- 로깅, 모니터링, 알림 시스템은 MVP 단계에서 구축하지 않는다.
- 성능 최적화를 하지 않는다. 느려도 동작하면 된다.

## 태스크 분해
- 기능 단위(회원가입, 로그인 등)가 아니라 **사용자 시나리오(end-to-end flow)** 단위로 쪼갠다.
- 예: "가입 → 핵심 기능 1회 사용 → 결과 확인" 전체가 하나의 태스크다.
- 한 태스크가 독립적으로 **데모 가능**한 것을 우선한다.
- 백엔드/프론트엔드를 분리하지 않는다 — 하나의 태스크에서 풀스택으로 끝낸다.
- **3개 이하의 태스크**로 첫 데모가 가능해야 한다. 태스크가 많으면 스코프를 줄여라.
- 데이터 모델은 최소한으로 — 필드가 10개 넘으면 다시 생각해라.

## 품질 기준
- **돌아가면 통과**. 그게 전부다.
- 테스트는 핵심 경로(happy path) 수동 확인 1번이면 충분. 자동화 테스트는 작성하지 않아도 된다.
- 코드 스타일, 린트 경고, 타입 완전성은 무시해도 된다.
- 보안은 최소한만 — 인증이 필요하면 가장 단순한 방식(예: 하드코딩된 API 키)으로 한다.
- 문서화하지 않는다. 코드가 곧 문서다.

## 리뷰
- 리뷰 1라운드 (또는 스킵 가능).
- **"이것이 핵심 가설을 검증하는가?"** 단 하나의 질문으로만 리뷰한다.
- 코드 품질, 아키텍처, 네이밍, 테스트 유무는 리뷰하지 않는다.
- 리뷰어가 "이걸로 가설 검증이 되겠다"고 판단하면 즉시 통과.

## 우선순위
```
속도 ≫ 기능 완성 ≫ 품질 ≫ 확장성
```
- 기술 부채를 의도적으로 허용한다.
- "2주 안에 버릴 수도 있는 코드"라는 마인드셋으로 작업한다.
- 피벗이 확정되면 처음부터 다시 만들 각오를 한다.
