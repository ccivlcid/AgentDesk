## 기술스택
- 기존 시스템: (예: Java/Spring, .NET, PHP, COBOL 등)
- 마이그레이션 대상: (예: Node.js, Go, 클라우드 네이티브 등)
- DB: (예: Oracle, SQL Server, PostgreSQL 등)
- 인프라: (예: 온프레미스, 하이브리드 클라우드, AWS/Azure 등)
- 컴플라이언스: (예: SOC2, HIPAA, GDPR, PCI-DSS, ISO 27001 등)

## 목표
운영 중인 대규모 시스템을 **아무것도 깨뜨리지 않으면서** 점진적으로 개선/마이그레이션한다.
이 프로젝트의 최고 성과는 "새 기능을 추가한 것"이 아니라 "기존 시스템이 안정적으로 유지되는 것"이다.

## 작업 원칙
- **기존 시스템 호환성이 절대 최우선**이다. 동작 중인 시스템을 깨뜨리면 매출 손실, 고객 이탈, 컴플라이언스 위반으로 이어진다.
- 변경 범위를 최소화한다. 한 번에 하나의 관심사(concern)만 변경한다. "겸사겸사 이것도 고치자"는 금지.
- **점진적 마이그레이션(Strangler Fig 패턴)**을 따른다. 새 시스템을 기존 시스템 옆에 세우고, 트래픽을 점진적으로 전환한 후, 기존 시스템을 제거한다.
- 모든 변경에 **영향 분석(Impact Analysis)** 문서를 선행한다. 이 변경이 어떤 테이블, 어떤 서비스, 어떤 팀에 영향을 주는지 파악한 후에만 구현을 시작한다.
- 롤백 계획 없이 배포하지 않는다. 롤백에 걸리는 시간까지 측정한다.
- 감사 로그(audit log)를 모든 데이터 변경에 적용한다. 누가, 언제, 뭘 바꿨는지 추적 가능해야 한다.
- 다른 팀/서비스와의 의존성을 명시적으로 문서화한다. 우리 변경이 다른 팀에 영향을 줄 수 있으면 사전 통지 필수.
- 하위 호환 레이어(adapter, shim, facade)를 먼저 만들고, 모든 클라이언트가 전환된 후에만 이전 코드를 제거한다.
- 데이터 마이그레이션은 코드 변경과 분리한다. 동시 배포 절대 금지. 데이터 먼저, 코드는 나중에.

## 태스크 분해
- 매 태스크마다 **5단계 사이클**을 따른다:
  1. **영향 분석**: 이 변경이 영향을 주는 범위(테이블, 서비스, API, 팀) 파악 + 문서화
  2. **변경 계획**: 구현 방법, 하위 호환 전략, 롤백 절차 수립
  3. **구현**: 계획대로 구현. 계획에 없는 변경은 하지 않는다.
  4. **회귀 테스트**: 변경한 부분뿐 아니라 영향 받는 모든 기능의 테스트 수행
  5. **롤백 계획 검증**: 실제로 롤백을 수행해보고, 소요 시간을 측정
- 한 번에 큰 변경보다 작은 변경을 여러 번 한다. Big-bang 배포는 금지.
- 하위 호환 레이어를 먼저 만들고(태스크 A), 클라이언트를 전환하고(태스크 B), 이전 코드를 제거한다(태스크 C). 이 세 단계를 하나의 태스크로 합치지 않는다.
- 각 태스크 완료 시 "이전 동작이 깨지지 않았음"을 증명하는 테스트가 반드시 포함되어야 한다.

## 품질 기준
- 영향 분석 문서 없이 구현 착수 **절대 금지**. 이것이 가장 중요한 규칙이다.
- 회귀 테스트 전체 통과 필수. 기존 테스트 하나라도 실패하면 머지 금지.
- 하위 호환성 보장. deprecation 경고 → 최소 1 릴리즈 기간 유지 → 이후 제거.
- 변경 로그 상세 기록. 누가, 언제, 왜, 무엇을 변경했는지. 추후 감사(audit)에 대비.
- 컴플라이언스 요구사항 체크리스트 통과. SOC2, HIPAA 등 해당 규정에 맞는지 확인.
- 성능 회귀 없음. 변경 전후 벤치마크를 비교한다. P95 응답 시간이 10% 이상 느려지면 머지 금지.
- 데이터 마이그레이션 시 데이터 무결성 검증 필수. 레코드 수, 체크섬, 샘플 비교.

## 리뷰
- **가장 깐깐한 리뷰. 전 부서 참여** (dev + qa + devsecops + operations + planning).
- 리뷰 관점:
  - **dev**: 이 변경이 다른 팀의 코드/서비스를 깨뜨릴 수 있는가?
  - **qa**: 회귀 테스트가 충분한가? 놓친 시나리오는 없는가?
  - **devsecops**: 보안/컴플라이언스 위반은 없는가?
  - **operations**: 배포 절차가 안전한가? 롤백이 가능한가?
  - **planning**: 비즈니스 영향은 무엇인가? 고객 공지가 필요한가?
- 롤백 계획의 존재 여부 + 실제 롤백 테스트 수행 여부를 리뷰에서 확인한다.
- 데이터 마이그레이션은 별도의 심화 리뷰를 수행한다.

## 우선순위
```
안정성 ≫ 보안 > 호환성 > 컴플라이언스 > 기능 > 속도
```
- 새 기능보다 기존 기능 보호. "아무것도 깨지지 않는 것"이 최고 성과.
- 일정 압박이 있어도 영향 분석과 회귀 테스트를 건너뛰지 않는다.
